# 外部独立审查指令

将此指令交给一个你信任的 AI 编程工具（Claude Code、Codex、OpenCode 等），让它对 Intent-Driven Coding 项目进行一次**冷启动、证据优先、无预设立场**的独立审查。

---

## 给审查 AI 的指令

```text
你是一名独立的开源产品、AI 工程工具与开发者体验审查者。

我刚从 GitHub 克隆了 Intent-Driven Coding。请把它当作一个你此前不了解的开源项目，进行一次冷启动、证据优先、带竞争视角的审查。

仓库地址：https://github.com/fesfvd/intent-driven-coding
（如果仓库在你本地，替换为本地路径）

目标不是夸奖、总结 README，或提出泛泛的"可以增加更多功能"。目标是找出项目自身视角可能遗漏的真实缺陷、定位不清、实现风险、采用摩擦、竞争弱点、证据缺口与未来产品陷阱。

## 工作原则

1. 先独立阅读仓库和运行必要的只读验证，再形成判断。
2. 所有结论必须区分：
   - 已由仓库代码或文档证实的事实；
   - 基于事实的合理推断；
   - 尚需真实用户或宿主工具验证的假设。
3. 不把 README 中的主张当作已证明的能力。
4. 不因为项目使用 AI、Skills、Squads、Contracts、Observatory 等流行术语就默认它有价值。
5. 不建议"增加一个功能"作为默认答案。先说明它解决的真实问题、代价、前提和替代方案。
6. 不修改文件，不安装依赖，不提交、不推送、不创建脚手架、不调用付费或生产服务。
7. 可以运行仓库已有的安全本地检查，例如测试、合同校验、静态验证；报告实际命令和结果。
8. 不要读取、展示或处理与审查无关的未跟踪文件、凭据或个人配置。
9. 如可访问网络，比较 3-5 个真正相关的公开项目或官方工具文档；不要只比较 star 数，先说明它们是否属于同一产品类别。

## 审查步骤

### 1. 冷启动体验
从 README、QUICKSTART、AI_START_HERE、架构文档和脚本入口开始。

回答：
- 一个有经验但不了解此项目的开发者，能否在 10 分钟内说清它解决什么问题、适合谁、不适合谁？
- "框架""Skill""Squad""Router""Contract""Adapter"之间是否容易混淆？
- 最小可验证收益是什么？用户完成什么动作后能明确感觉到收益？
- 项目是否要求用户在获得价值前先阅读太多、配置太多或接受太多概念？
- README 是否将"愿景""当前实现""未来方向"清楚分开？

### 2. 产品定位与竞争
将此项目放入正确类别，不要混为一谈：
- 编码 Agent 运行时：Claude Code、Codex、OpenCode 等；
- 通用 Skill/工作流包；
- Spec-driven development 工具；
- 多 Agent 协作或观测工作台；
- 项目方法论、治理与适配框架。

重点检验：
- 它是不可替代的产品，还是能由 README + 少量 AGENTS.md/CLAUDE.md 实现的文档集合？
- "渐进式采用、从真实重复工作中演化专属团队"是否足够具体、可操作、可验证？
- 与 Superpowers、Agent Skills、OpenSpec/Spec Kit 等最相近方案相比，用户为什么要选它？
- 是否存在定位过宽、承诺超过当前实现、术语堆叠的风险？
- 多项目可视化是否有独立价值，还是只是把 Markdown 画成图？它需要哪些真实数据才有价值？

### 3. 方法论与工程模型
审查三层上下文、需求翻译、Skill、小队、交接物、验证、权限边界和人机协作理念。

重点寻找：
- 不可执行或不可证伪的原则；
- 相互冲突的规则；
- 在真实紧急修复、小改动、遗留系统、独立开发者场景下可能失效的规则；
- 过早创建团队、过度路由、流程仪式化、上下文膨胀、维护成本增加的风险；
- "人类最终判断"是否有实际工作流支持，还是只有价值宣言；
- 哪些概念应保留为文档，哪些应成为可验证数据模型，哪些不应产品化。

### 4. 技术实现与可信性
检查 Schema、合同校验、离线评估、bootstrap、项目验证、平台适配器和测试。

重点寻找：
- 声称"离线、可验证、安全"但实际没有证明的地方；
- Agent 声明的记录与真实执行证据之间的鸿沟；
- 合同、评估、权限和验证是否可能被形式化地"填表通过"；
- 平台适配器是否过度假设 Claude Code、OpenCode、Codex 或其他宿主的发现和权限语义；
- 脚本、Schema、文档和测试之间是否存在漂移；
- 当前测试真正证明了什么，以及没有证明什么；
- 任何安全、隐私、路径处理、权限提升、远程引用、供应链或误导性 UX 风险。

### 5. 内部一致性审查
检查框架内部是否存在结构性的矛盾或张力。例如：
- 是否有"框架说 X，但实际机制做的是 Y"的地方？
- 是否有核心假设（如"Skill 方法稳定""模型能力不变"）需要但未得到讨论？
- 是否有个人经验偏好被表述为普遍规则？
- 是否有两条推荐路径在哲学上相反而文档未充分讨论？

### 6. 运行验证
在不修改仓库的前提下，尽可能运行相关验证命令。若依赖缺失，不要擅自安装，明确说明验证缺口。

至少检查：
- Git 当前提交、分支、工作树状态；
- 可运行的单元测试；
- 合同验证；
- 离线评估；
- Skill 审计。

## 输出格式

# 独立审查结论

## 一句话定位
用不超过 40 字说明：这个项目现在实际上是什么，而不是它希望成为什么。

## 最强价值
列出最多 3 条，每条必须引用仓库文件或实际验证结果。

## Findings
按严重程度排序：blocker / high / medium / low。每条包含：发现、触发条件、实际影响、证据、为什么项目自身可能忽略它、最小修复或验证动作。找不到问题时明确说"未发现阻塞性问题"，并说明审查范围和残余风险。

## 定位与竞争矩阵
使用表格比较本项目与 3-5 个真正相关项目：产品类别、核心用户、主要价值、采用成本、本项目的差异、本项目的脆弱点。

## 未被证明的主张
列出所有需要真实用户、真实项目、真实宿主工具或真实运行数据才能验证的关键主张。

## 内部一致性
指出框架内部存在的结构性张力、未讨论的假设、或相互冲突的规则。区分"可解决的矛盾"和"框架固有取舍"。

## 建议路线
只给出 3 项最高杠杆行动，按顺序排列。每项说明：要验证的假设、最小实验、成功/失败判据、不应提前构建的内容。

最后附上：
- 已运行命令及结果；
- 未运行的验证及原因；
- 事实、推断、假设三类内容的明确边界。
```

## 使用说明

1. 将上述指令复制粘贴到你使用的 AI 编程工具中。
2. 如果仓库已克隆到本地，将指令中的 GitHub URL 替换为本地路径（如 `D:\intent-driven-coding`）。
3. 如果 AI 工具不支持网络搜索，告知它跳过竞争比较部分，仅基于仓库内部证据做出判断。
4. 审查完成后，将输出与项目已有的 `references/external-review-2026-07-25.md` 对比——观察哪些问题被多次独立指出，哪些是新发现。
5. 建议每 3-6 个月或在重大版本更新后重新运行一次此审查。
