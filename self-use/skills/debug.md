# Debug 方法（系统化 Bug 诊断）

> 用于未知根因的 bug。如果你已经知道原因，直接修复即可。

---

## 何时使用

✅ **应该用：**
- 有报错/异常行为，但不知道原因在哪
- "它就是不工作"
- 生产问题需要留诊断记录

❌ **不需要用：**
- 已知根因（如 "typo in line 45"）
- 简单的语法错误
- 编译器/linter 已经指出问题

---

## 三步定位法

### 第 1 步：可靠复现（Reliable Reproduction）

**目标：** 用最简命令稳定触发问题

**操作：**
```bash
# 记录复现步骤
[你的命令或操作步骤]

# 预期结果
[应该发生什么]

# 实际结果
[实际发生了什么]

# 错误信息（如果有）
[完整错误堆栈，不要截断]
```

**检查点：**
- [ ] 能 100% 复现（不是"有时会出错"）
- [ ] 记录了完整的错误信息或异常行为
- [ ] 最小化了复现步骤（去掉无关操作）

---

### 第 2 步：二分定位（Binary Search for Break Point）

**目标：** 找到第一个"断裂点"—— 输入正常、输出异常的那一层

**数据流分层（根据项目调整）：**
```
用户操作 → 前端组件 → API 路由 → 业务逻辑 → 数据层 → 数据库
         ↓ 在哪一层开始出错？
```

**定位方法（优先级递减）：**

1. **查看日志**
   ```bash
   # 应用日志
   tail -n 100 logs/app.log
   
   # 如果有集中式日志
   [你的日志查询命令]
   ```

2. **添加调试输出**
   ```javascript
   // 在关键节点打印变量
   console.log('[DEBUG] userId:', userId, 'data:', data);
   ```

3. **单元测试隔离**
   ```bash
   # 单独测试可疑模块
   npm test -- UserService.test.js
   ```

4. **断点调试**
   ```
   IDE 断点 → 逐步执行 → 观察变量值何时变异常
   ```

**输出：** 明确定位到具体的文件和行号

---

### 第 3 步：假设验证（Hypothesis Testing）

**目标：** 形成可证伪的假设，并验证

**反例（不可证伪的假设）：**
❌ "可能是数据问题"  
❌ "应该是并发导致的"  
❌ "感觉是缓存没清"

**正例（可证伪的假设）：**
✅ "如果 userId 为 null，会在 UserService.java:45 抛出 NullPointerException"  
✅ "当 report.data 为空数组时，序列化层返回空字符串而不是 '[]'"  
✅ "Redis 连接超时时，代码未捕获异常导致整个请求失败"

**验证步骤：**
1. 构造测试输入（能触发假设的输入）
2. 运行并观察结果
3. 如果行为符合假设 → 找到根因
4. 如果不符合 → 修正假设，重新验证

---

## 输出交接物

诊断完成后，生成 `.idc/tasks/{task-id}/diagnosis.md`：

```markdown
# Bug 诊断报告

## 症状
[用户可观察到的错误行为]

## 复现步骤
1. [步骤 1]
2. [步骤 2]
3. 观察到：[错误]

复现命令：
\`\`\`bash
[完整命令]
\`\`\`

## 定位过程

### 调用链追踪
[入口] → [中间层] → [断裂点]

### 关键日志/调试输出
\`\`\`
[粘贴相关日志片段]
\`\`\`

### 断裂点
- 文件：[文件名]
- 行号：[行号]
- 函数/方法：[名称]

## 根因
**假设：** [一句话描述根本原因]

**证据：** [如何验证的]

**影响范围：** [哪些场景会触发]

## 修复方向
[简要说明修复思路，不是详细实现]
```

## 常见陷阱

### 陷阱 1：过早假设根因
❌ 看到 NullPointerException 就认为"加个 null 检查"  
✅ 先找到为什么会是 null（上游哪里传错了）

### 陷阱 2：依赖"感觉"
❌ "我觉得是并发问题"（没有并发场景的证据）  
✅ 用日志/调试器证实是否真的有并发访问

### 陷阱 3：跳过复现步骤
❌ "用户说有问题，我猜是 X"  
✅ 先自己复现，确认问题真实存在

### 陷阱 4：修改太多地方
❌ 一次改 5 个"可能有问题"的地方  
✅ 定位到精确断裂点，最小化修改

## 门禁检查

<HARD-GATE>
在提出修复方案前，必须完成：

- [ ] 能可靠复现问题（100% 触发率）
- [ ] 定位到具体的文件和行号
- [ ] 给出可证伪的根因假设
- [ ] 验证了假设（不是猜测）
- [ ] 生成了诊断交接物

如果以上任何一项未完成，不允许进入实现阶段。
</HARD-GATE>

---

## 时间预估

| 复杂度 | 预计时间 | 典型场景 |
|--------|---------|---------|
| 简单 | 5-10 分钟 | 日志直接指出问题，单点故障 |
| 中等 | 10-20 分钟 | 需要追踪调用链，逐层排查 |
| 复杂 | 30-60 分钟 | 并发/时序问题，需要构造特殊场景 |

如果超过 60 分钟仍未定位，考虑：
1. 寻求有经验的开发者帮助
2. 添加更详细的日志后重新部署
3. 使用 profiler / APM 工具

## 实际案例示例

**症状：** 报表保存后显示空白

**复现：**
```bash
1. 登录系统
2. 打开报表页面
3. 点击"保存"按钮
4. 页面刷新后，报表内容为空

复现率：100%（每次都会）
```

**定位过程：**
```
用户操作 → ReportView.tsx (前端) → API /api/reports/save
         → ReportController.save() → ReportService.serialize()
         → ReportSerializer.toJSON() ← 断裂点在这里

日志显示：
  [INFO] Saving report id=123, userId=456
  [DEBUG] Report data before serialization: [Object with 15 fields]
  [DEBUG] Serialized result: ""  ← 空字符串！
```

**根因假设：**
"当 report.customFields 为 null 时，ReportSerializer.java:67 的 JSON 转换返回空字符串而不是默认空对象"

**验证：**
```java
// 构造测试用例
Report report = new Report();
report.setCustomFields(null); // 设置为 null
String json = serializer.toJSON(report);
System.out.println(json); // 输出：""（空字符串）

// 确认假设成立
```

**诊断交接物：** 已生成 `.idc/tasks/20260909-001/diagnosis.md`

**修复方向：** 在 ReportSerializer.java:67 添加 null 检查，返回默认空对象 `{}`
