# Architecture 方法（跨层变更设计）

> 用于涉及 3+ 文件、跨层数据流、API 契约、数据库结构或共享状态的变更。
> 单文件、无契约影响的小改动不需要这个方法。

---

## 何时使用

✅ **应该用：**
- 新增/修改 API 契约（请求或响应结构变化）
- 涉及数据库 schema、迁移、索引
- 跨层改动（前端 → 路由 → 服务 → 数据层）
- 共享状态、缓存、事件流、定时任务
- 你不确定"改这里会不会影响别处"

❌ **不需要用：**
- 改文案、颜色、日志级别
- 单文件、无外部契约的局部修复
- 只读探索（先探索清楚了再决定要不要用）

---

## 第 0 步：先追现状，再谈方案

**规则：先证明你理解当前系统怎么工作，才有资格设计改动。**

必须落到真实代码，不允许"一般来说这种项目都是……"。

| 追踪项 | 要回答的问题 | 证据形式 |
|--------|-------------|---------|
| 生产入口 | 请求/事件从哪里进来？ | 文件:行号 |
| 调用链 | 经过哪几层，每层做什么？ | 入口 → 中间 → 落点 |
| 持久化 | 读写哪些表/文件/缓存键？ | 表名、schema、读写的字段 |
| 消费者 | 谁依赖当前行为？ | 前端、其他服务、脚本、报表 |
| 生成物 | 有哪些是生成而非手写的？ | 生成命令 + 源文件 |
| 验证资产 | 已有测试覆盖到哪一层？ | 测试文件 + 覆盖路径 |

**优先使用仓库索引工具**（如 CodeGraph 一类的符号/调用图索引）：一次结构化查询往往比多轮全文搜索更准，还能跟到动态分派。索引不可用时再用 Read/Grep/Glob。

**输出：** 一张当前数据流图（可以是 ASCII），每一跳都有文件依据。

---

## 第 1 步：划影响半径

把改动拆成三类，逐条列出：

1. **改写**：哪些现有函数/接口的行为会变？（列出调用方）
2. **新增**：新文件、新接口、新字段、新表。
3. **删除**：什么会消失？（这最危险，必须先列）

**兼容性三问：**
- 旧客户端/老数据还能用吗？
- 部署是原子的吗？中间态会不会崩？（灰度/双写在不在考虑范围）
- 回滚时数据还能读回来吗？

**生成物检查：** 如果改动涉及 schema、模板、代码生成，必须同时改源头并重新生成，不能手改生成文件。

---

## 第 2 步：方案对比与决策记录

**至少给出 2 个方案**（包括"最小改动方案"）。只有一个方案时，说明为什么另一个不可行。

每个关键决策按这个结构写：

```
## 决策 N：[问题]
**背景：** [当前状态与痛点，带证据]
**目标：** [可验证的结果，不是"更好"]
**候选：**
- A. [方案] — 优点 / 缺点 / 成本
- B. [方案] — 优点 / 缺点 / 成本
**选择：** A
**理由：** [权衡依据，说清放弃了什么]
**何时该反悔：** [什么证据出现说明这个选择错了]
```

**必须标"建议"的内容：** 命名、默认值、格式、超时时间、TTL、分页大小——这些是建议默认，不是你替用户做的产品决定。真正影响产品语义、权限、数据保留期的选择，列成开放歧义问用户。

---

## 第 3 步：失效、边界与回滚

- **失败模式**：这个改动怎么坏？网络超时、并发写、部分成功、依赖不可用。
- **失效处理**：降级、重试、补偿、人工介入点，各选一个并说明。
- **可观测**：出问题时靠什么发现？（日志字段、指标、错误码）
- **回滚路径**：代码回滚够不够？数据需要反向迁移吗？

## 常见陷阱

### 陷阱 1：从模板开始，而不是从代码开始
❌ "一般这种分层项目，Service 层放业务逻辑，我就在那里加一个方法"
✅ 先读真实调用链，发现这个项目把校验放在 Controller 的拦截器里

### 陷阱 2：只想到新增，没想到删除
❌ 只列出要加什么
✅ 明确列出旧字段/旧接口什么时候可以删、谁还在用

### 陷阱 3：把建议当成需求
❌ "所以我用了 Redis，TTL 30 分钟"（用户从没说过）
✅ "建议用 Redis，TTL 30 分钟（重复查询占比 78%）。这是建议默认，你可以改"

### 陷阱 4：只设计成功路径
❌ 流程图画的全是绿灯
✅ 每个外部调用都标注失败时怎么办

### 陷阱 5：手改生成物
❌ 直接改生成出来的 schema/客户端代码
✅ 改源定义 + 重新生成 + 确认 diff 只有预期变化

## 门禁检查

<HARD-GATE>
在进入实现阶段前，必须完成：

- [ ] 追出了当前数据流，每一跳都有文件依据
- [ ] 列出了改写/新增/删除三类影响，含调用方
- [ ] 至少 2 个方案对比，或说明为何只有一个可行
- [ ] 关键决策写了理由和放弃的代价
- [ ] 影响产品语义/权限/数据的选择已问过用户
- [ ] 兼容性与回滚路径明确
- [ ] 生成了 architecture.md 交接物

任何一项未完成，不允许开始写实现代码。
</HARD-GATE>

## 时间预估

| 复杂度 | 预计时间 | 典型场景 |
|--------|---------|---------|
| 简单 | 10-15 分钟 | 单接口加字段，调用方 1-2 处 |
| 中等 | 20-40 分钟 | 跨 2-3 层，含迁移或缓存 |
| 复杂 | 1-2 小时 | 契约变更 + 数据迁移 + 多消费者 |

超过预估仍未收敛时：
1. 缩小范围，先交付一个可验证的最小切片
2. 把开放歧义直接抛给用户，不要自己填
3. 记录当前假设，说明哪些还没证实
